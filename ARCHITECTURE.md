# Monechai architecture (work in progress)

Current implementation/acceptance map is in the [new-session plan](docs/PROJECT_RECORD.md#current-readiness-and-next-session-plan). The admin now has a dedicated workspace, inline category creation, product photo preview/media controls, inventory view and actual order/COD reports. Owner login/AAL2 access is verified; real photo/product/order, recovery/session and operations acceptance remain. Visitor/conversion/profit tracking is not implied by the new reports.

One Next.js 16 App Router / TypeScript **modular monolith**: `src/app` routes and layouts; `src/components` UI; `src/features/catalog`, `cart`, `checkout`, `admin` domain operations; `src/db/schema` and checked-in Drizzle SQL migrations; `src/i18n` translations; `src/lib` environment, shared utilities and Supabase clients; `src/proxy.ts` session refresh. PostgreSQL stores products, orders and settings; Supabase Auth provides identity; `admin_members` is the explicit authorization whitelist. Supabase Storage is the intended home for real product images. Local upload, decode, publish gating and the Storage policy artifact exist; a live owner bucket has not been accepted. Managed PostgreSQL/Supabase is external to the VPS. See [deployment](docs/deployment.md) and [bootstrap](docs/admin-bootstrap.md).

## Data and request boundaries

- `catalog`: categories → products → variants (SKU, integer minor-unit price and stock) and images. Demo imports are drafts; only published products with real primary images should be publicly purchasable. Public queries page/filter on the server, not a client-side full-catalog download.
- `cart`: browser storage holds **variant IDs and quantities only**, never lasting customer PII or authoritative prices. The client preview is advisory.
- `checkout`: API validates customer input, stock, owner-configured shipping zone and server-side price. PostgreSQL transaction locks inventory and inserts order, item snapshots and idempotency record; duplicate keys return the existing order only for an identical request. Any failure rolls back and must not generate a success screen. Public success links use opaque tokens rather than sequential order IDs; they are sensitive and must not be logged.
- `orders`: immutable line snapshots preserve product name/SKU/attributes/unit and line amount after catalog edits; status and COD payment updates go through privileged admin functions with transition checks/history. Browser cannot choose status or mark orders paid. No bKash/Nagad gateway exists.
- `admin`: Supabase SSR cookies identify an Auth user; each privileged DB operation rechecks membership with server-only `requireAdmin()`, not just layout gating. The first member is bootstrapped through owner-only SQL; there is no public admin registration. Migration 0006 enables RLS and revokes client API grants on the application tables. Secrets belong only on the server.
- `media`: catalog storage keys reference the public `products` bucket. Admin upload re-encodes images, records a content hash, and publish requires a matching primary object plus an active variant. Reviewed Storage policies live in `ops/supabase-storage.sql`. The live bucket/policy baseline is recorded in [Supabase handoff](docs/SUPABASE_SETUP_HANDOFF.md); actual owner upload and provider authorization acceptance remain required. Placeholder demo images stay unpublished.
- `site`: `site_settings` hold verified business contact, support and SEO text; shipping fees live in `shipping_zones`, never in a client constant. EN/BN strings use `src/i18n` and localized catalog fields. Localized routes, policy revisions and configured store-name branding are implemented locally. Approved business copy and actual provider/host acceptance remain required under [goal 08](docs/PROJECT_RECORD.md#goal-08).

## Deployment and observability

`Dockerfile` builds `.next/standalone` in Node 22; runtime uses a non-root user, with `.next/static` and `public` copied explicitly. Reverse proxy terminates TLS and keeps port 3000 private; `NEXT_PUBLIC_*` variables are build-time public values. Runtime `DATABASE_URL` is secret; migrations run separately with `DIRECT_URL`. Preflight runtime readiness uses only `DATABASE_URL`; operator history verification uses only `DIRECT_URL`. Default full release preflight requires both; `--runtime-only` explicitly leaves migration history unverified. Operator credentials stay outside app runtime/build environments. `/api/health` checks DB connectivity and returns 200/503 without user data. Application logs should contain only event names, never PII or credentials. Single-instance deployment is the documented default; multiple instances need coordinated Next cache invalidation and server function keys. See [recovery](docs/backup-recovery.md) for DB **and** object backup obligations.

## Non-negotiable invariants

1. Client price, shipping and stock are not authoritative. Only the server computes totals and decrements stock.
2. Orders are transactional and idempotent; failed writes never yield success. Historical order item snapshots remain immutable.
3. Payment and order statuses cannot be arbitrarily set by a browser; COD is the only active payment method.
4. Admin authorization is enforced inside every server operation. A user session alone is insufficient.
5. Products are created/edited in admin without source edits. No secret is exposed in a client bundle, and customer PII is not stored permanently in localStorage.

This is an architecture record, not a sign-off: goals03/04 are complete locally;05–09 require actual owner/backend/business acceptance;10 has upstream/tooling and production acceptance gates;11 requires gateway choice/access. The obsolete static runtime was removed during the 2026-10-10 owner-requested cleanup; the old design remains in Git history and unpublished seed data lives in `fixtures/demo-catalog.json`. See the [immutable 2026-10-14 audit baseline](docs/audits/2026-10-14-monechai-production-readiness-audit.md) and [current remediation status](STATS.MD) for commerce/security findings and later fixes. The app currently supports one store owner; seller tenancy, commissions and payouts are absent.

## New boundaries (2026-10-11)

Locale-specific StoreShell under `app/[locale]` avoids persistent-root language bugs; proxy sanitizes locale/visitor headers and only real document visits update preference, preventing prefetch races. Metadata and Product JSON-LD use localized canonical/alternate URLs and effective prices. Public indexing defaults to denied. `SITE_INDEXING_APPROVED_ORIGIN` is a server-only owner approval: it must exactly match the clean HTTPS `NEXT_PUBLIC_SITE_URL`, with `NODE_ENV=production` and `VERCEL_ENV=production` when that provider marker is present. Leave approval unset for staging/preview/test. Metadata, robots and sitemap share this policy; approval never makes private routes indexable. See [indexing configuration](docs/deployment.md#search-indexing-approval). Receipt pages remain limited bearer access (not phone identity verification), never include customer PII and use private/no-store/no-referrer/noindex; nginx access format omits URLs/queries/cookies.

`store_policies` holds retained approved revisions; orders store immutable consent revision/time. Publish/read/consent changes use transactions/shared locks; new checkout is blocked without approved policies. `order_notifications` is a unique order-linked transactional outbox. A private worker leases one event, sends owner-only SMTP mail, retries/backoffs and retains failed events for MFA-protected admin retry. At-least-once mail may duplicate after uncertain acknowledgement; it never recreates an order or marks payment paid.

Local batch03 adds migration0013 and append-only `admin_mutation_history` for material catalog/inventory/media/tracking/settings/policy changes. Server-verified admin identity is scoped to the database transaction; allowlisted triggers commit history with the change. Runtime receives SELECT only, API grants remain revoked. Text fingerprints/contact redaction limit retained data, and existing order histories remain intact. Live migration and owner retention/access acceptance remain pending; see [database history boundary](docs/database-security.md#administrative-mutation-history--mon-018).

Owner recovery verifies provider recovery OTP, membership and any enrolled TOTP/AAL2 before password update; admin operations always require AAL2 and private Storage helpers/restrictive product write guards enforce the same requirement even against old permissive policies. Real JWT/provider behavior remains an acceptance gate.

Application backups export public/drizzle and referenced photo bytes under one SQL snapshot and authenticate encryption/content. Restore drills are confined to empty local named databases. This is not full Supabase Auth/bucket/role recovery or configured off-site/scheduled production backup. See [operations checks](docs/OPERATIONS_CHECKS.md) and [owner setup checklist](docs/PROJECT_RECORD.md#owner-setup-checklist).
