# Server database boundary

Migration 0006 enables RLS on every application table and revokes client API role privileges (`anon`, `authenticated`, `service_role`, plus PUBLIC). The storefront/admin use direct PostgreSQL through the Node server. Supabase Auth identifies the admin; it does not grant direct table access to customer browsers.

Use a separate migration/owner connection. For production, provision a dedicated server login through an authorized operator with a generated secret and grants/policies restricted to the application's tables. Never use an `anon`/`authenticated` API role as DATABASE_URL. No blanket public-read policy is needed because published catalog data is served through Next. RLS must remain enabled on future tables and new migrations must revoke API grants too.

The local disposable database tests use the table owner, and a non-owner granted test role verifies RLS denies SELECT/UPDATE/DELETE plus INSERT of a dummy settings row. Live Supabase Data API verification is still required before launch. Owner bootstrap remains a separate privileged action; don't give the runtime role write permission to admin_members.

Deploy only after reviewing permissions for both runtime and migration roles. If the runtime is non-owner, explicit role-specific RLS policies must authorize its needed operations. Keep order item/history updates constrained; do not grant client API keys access to orders, settings or stock. Storage policies for the `products` bucket are in `ops/supabase-storage.sql` and [product image setup](product-images.md). Apply them on the owner project; local tests model those identities and do not replace a live bucket check.

MON-002 preflight boundary: application readiness queries run only as `DATABASE_URL`; migration-history count runs only as separately injected operator `DIRECT_URL`, with no fallback. Runtime retains the exact restrictions in [runtime SQL](../ops/supabase-runtime.sql), including no `drizzle` USAGE or membership writes. A history-only operator requires CONNECT, `drizzle` USAGE and SELECT on `drizzle.__drizzle_migrations`, not application-table access or metadata writes. Full release preflight fails if history verification is unavailable; explicit `--runtime-only` success is narrower evidence. Both sessions default to read-only. See [commands and acceptance limits](OPERATIONS_CHECKS.md#release-checks). PostgreSQL separates [schema USAGE and table SELECT](https://www.postgresql.org/docs/17/ddl-priv.html); [default_transaction_read_only](https://www.postgresql.org/docs/17/runtime-config-client.html) adds a session safeguard, not a replacement for grants. Live exact-role/TLS/project acceptance remains external; no production role/grant change is required for this source fix.

## Administrative mutation history — MON-018

[Migration 0013](../src/db/migrations/0013_admin_mutation_history.sql) adds `admin_mutation_history` with RLS, API/PUBLIC revokes, bounded JSON changes and resource/time indexes. Existing migrations remain unchanged. Apply it later through an authorized owner/migration connection, before running the new admin code; batch03 validates only a disposable PostgreSQL database. It does not update the live Supabase baseline. The migration grants an existing `monechai_runtime` SELECT only; [runtime provisioning](../ops/supabase-runtime.sql) grants the same access for newly provisioned roles. Runtime cannot insert, update or delete history, write membership, or execute the audit function directly. No public/API route serves audit data.

Each material admin action still calls `requireAdmin()` to verify Auth user, current membership and AAL2. Its server-derived ID becomes transaction-local `monechai.admin_actor` through [the mutation helper](../src/features/admin/mutation-history.ts). Membership is rechecked inside the transaction and again by each trigger. Form/body actor fields are ignored. Nine fixed-path `SECURITY DEFINER` triggers write committed catalog/category/variant/inventory/media/tracking/settings/zone/area/policy differences; audit failure rolls back the corresponding database change. Missing actor context records nothing for trusted operator/seed/checkout writes. Direct database credentials are the trusted server boundary, not proof of Supabase identity or MFA. A compromised owner or server/database credential can still bypass application authorization; this is not a tamper-proof ledger.

Only changed allowlisted fields are retained. Numbers, flags, UUID relationships and controlled shipping-zone enums retain previous/new values. Free text, including courier references, descriptions, policy content and attributes, retains SHA-256 fingerprints of PostgreSQL JSON values rather than another copy of the text. For settings contact fields and Storage keys, history records that the field changed with `redacted` previous/new markers; it cannot reconstruct their values. Customer names/contact/addresses/notes, receipt tokens, credentials and request bodies are excluded. Fingerprints support comparison with retained source revisions but are not encryption and cannot reconstruct overwritten text. Actor UUIDs and resource identifiers remain protected operational data. Order status/payment/inventory-release tables remain the authoritative histories for their respective changes; checkout, cancellation and returns do not create duplicate admin stock events. Identical saves produce no event; identical policy publication retains the existing consent revision. Storage removal runs after its own database commit, and failed upload metadata writes retain existing cleanup behavior.

Access is limited to the trusted Node runtime's SELECT privilege and authorized database operators. Any future admin history reader must call `requireAdmin()` and return bounded results. No viewer, export endpoint, scheduled purge or new logging vendor is added. History survives resource deletion because resource/actor IDs have no cascading foreign keys. Existing backup exports of the public schema include it, so backup access and deletion obligations also apply. Database owners can alter/delete records; application runtime and Data API roles cannot.

Retention is deliberately unconfigured pending owner acceptance under MON-009. Rows remain until an authorized operator applies an owner-approved retention/deletion policy; the application performs no automatic deletion and makes no promised retention period. Before production acceptance, approve a period and purpose for primary history, existing order histories and backups; document operator access, deletion exceptions and restore behavior. Review row growth with the time index. Do not invent a legal duration or purge immutable purchase/policy records to solve audit retention.

Design references: [OWASP logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html), [PostgreSQL transaction-bound triggers](https://www.postgresql.org/docs/17/sql-createtrigger.html), and [function security/search-path guidance](https://www.postgresql.org/docs/17/sql-createfunction.html). Local tests model the actual Server Action/auth source with a fixture provider plus real PostgreSQL runtime/API role controls; they do not establish live Supabase JWT, MFA, Data API or owner-session acceptance.
