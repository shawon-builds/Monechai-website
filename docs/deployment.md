## Owner prerequisites and configuration

- A Linux VPS with supported Docker (or Node 22 + npm), outbound TLS access to the database and Supabase; domain and TLS via an origin certificate/Let's Encrypt, optionally Cloudflare proxy. No database needs to run on the VPS.
- `DATABASE_URL` — **SECRET**, PostgreSQL app connection using the restricted runtime role, from Supabase Dashboard → Connect with the reviewed runtime identity. `DIRECT_URL` — **SECRET**, separate operator connection for migrations/history checks, injected only into trusted operator jobs; never replace the runtime identity with it or put it into the app environment. A history-only checker needs database CONNECT, `drizzle` USAGE and SELECT on `drizzle.__drizzle_migrations`; a migrator needs separately reviewed DDL privileges. `DATABASE_SSL=require` for Supabase; `disable` **only** on private/local PostgreSQL. Do not expose either URL in Docker build args, logs or `NEXT_PUBLIC_*`.
- `NEXT_PUBLIC_SITE_URL` — **PUBLIC**, verified canonical HTTPS origin, e.g. `https://shop.example.com`, **no path**. `NEXT_PUBLIC_SUPABASE_URL` — **PUBLIC** project URL; `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` — **PUBLIC** publishable key (Supabase Dashboard → Project Settings → API / Connect). Pass these **before build** and also at runtime; they are inlined into client JS and image host config. Never use a service-role key here. Configure Supabase Auth site URL/redirect allowlist to the actual HTTPS domain and create/invite an owner Auth user per [admin bootstrap](admin-bootstrap.md).
- Inspect the recorded [Supabase baseline](SUPABASE_SETUP_HANDOFF.md) first. A `products` bucket and policies were already applied to that exact project; verify them before repeating setup. For a separately approved new backend, create a public bucket named `products` and apply the reviewed policies in [`ops/supabase-storage.sql`](../ops/supabase-storage.sql) before publishing. Local upload, reorder, primary, remove and publish checks passed; live bucket and owner acceptance have not. Follow [product images](product-images.md). No payment keys: only COD is implemented. The store is not ready for real orders while goals remain paused or blocked.
- Owner must configure real shipping zone rates and contact/business settings before accepting checkout. `scripts/configure-shipping.mjs` requires owner-approved `SHIPPING_INSIDE_DHAKA_MINOR`, `SHIPPING_OUTSIDE_DHAKA_MINOR` and optional `SHIPPING_FREE_ABOVE_MINOR` (integer poisha). Dry-run with `npm run shipping:configure` before `npm run shipping:configure -- --apply`; see [checkout goal](PROJECT_RECORD.md#goal-04). Never use demo seed on production.
- Store runtime secrets in a root-readable env file outside the checkout, e.g. `/etc/monechai/runtime.env` (`chmod 600`), not in git or the Docker image; give only authorized operators access to Docker, which can inspect container environment. Public build args are visible in image history and should **never contain secrets**.

## Search indexing approval

For certificate verification, provide server-only `DATABASE_SSL_CA` containing the PEM CA certificate linked by the exact project's Database → Settings → SSL configuration. App and preflight then use `rejectUnauthorized: true`, including hostname verification. `DATABASE_SSL=require` without this CA retains the driver's encryption-only behavior; it does not verify server identity. Quote a multiline PEM with dotenv-compatible newline escapes, and inject it at runtime/operator startup alongside the relevant connection. The CA is public trust material; URLs/passwords remain secret. No system trust-store change or paid IPv4 add-on is required for the shared session pooler. Read-only connection checks must name the exact project and identity; they do not establish owner Auth/MFA or checkout acceptance. [Supabase connection/SSL guidance](https://supabase.com/docs/guides/database/connecting-to-postgres#ssl).

Production preflight also requires `CHECKOUT_TRUST_PROXY_IP_HEADER=true`. Set it only after testing the selected ingress: overwrite `X-Real-IP` from its verified peer/real-IP module, reject direct Node access, and verify forged `X-Real-IP`, `X-Forwarded-For`, `Forwarded` and `CF-Connecting-IP` cannot select the budget. In configured mode, missing/invalid single IP denies checkout/preview with503 and account rate checks deny; no visitor-cookie downgrade. IPv6 textual aliases and IPv4-mapped addresses share a canonical counter. Without configuration, visitor fallback remains resettable and is not launch acceptance. The preflight flag cannot prove network topology. No Monechai host/ingress is currently verified.

COD orders reserve stock while `pending_confirmation`; existing authorized manual cancellation releases inventory once within its transaction. No automatic expiry/cancellation policy exists. Owner must approve review cadence, customer-contact process and any future expiration rules before automation. Monitor the admin pending list and use existing cancellation/history rather than editing stock directly. No CAPTCHA/OTP/service or new quota business threshold was introduced. See [batch04 evidence](audits/2026-10-14-monechai-external-access-inventory.md) and [dependency maintenance](dependency-maintenance.md).

Public storefront indexing is default-deny. Owner must approve the exact real production origin before setting server-only `SITE_INDEXING_APPROVED_ORIGIN` equal to `NEXT_PUBLIC_SITE_URL` (for example, both `https://shop.example.com`). Approval must be an exact clean HTTPS origin without credentials, path, query, fragment or port. Localhost, IP addresses and `.local`/`.internal`/`.test` hosts are ineligible. `NODE_ENV` must be `production`; if `VERCEL_ENV` is present it must also be `production`. Missing, malformed, mismatched or inappropriate configuration keeps public metadata noindex, robots disallowed and the sitemap empty.

Set approval in the reviewed production server environment only after the owner approves that hostname. For Docker, inject it through the protected runtime env file alongside the matching `NEXT_PUBLIC_SITE_URL`; no approval build argument is required because indexing policy is evaluated when routes render. Keep the public canonical origin consistent with its existing build-time value. Leave it unset for staging, previews, tests and alternate hostnames. Do not copy production approval into a preview deployment. Public `NEXT_PUBLIC_SITE_URL` alone never approves indexing.

After separately authorized production deployment, inspect both locales' metadata, paginated shop canonicals/alternates, robots and sitemap against the approved origin. Admin, checkout, receipt and private routes remain noindex; authentication, authorization and private caching protections enforce their data boundaries independently of robots. No hostname, DNS, hosting provider or production approval is inferred from this runbook.

## Release procedure

1. Back up and confirm a restore point using [backup runbook](backup-recovery.md). Pin an immutable git revision and review changes to `src/db/migrations`. Take the shop offline for incompatible schema changes; use additive, backwards-compatible migrations for zero-downtime updates. Do not regenerate a migration against live data to resolve drift.
2. On a trusted deploy workstation/CI with **migration-only secrets**: `npm ci`, then `npm run db:migrate` with `DIRECT_URL` injected from the secret manager (not as a literal shell command). Verify migration success and review SQL **before** deploying app. Do not include production DB URLs in shell history or CI logs; use masked secrets/injected environment. To run demo data in disposable development only: `npm run db:seed` (refuses production).
3. Build: `docker build --build-arg NEXT_PUBLIC_SITE_URL=https://shop.example.com --build-arg NEXT_PUBLIC_SUPABASE_URL=https://PROJECT.supabase.co --build-arg NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=PUBLIC_KEY -t monechai:REVISION .`. Promote that exact image rather than rebuilding with different public settings. Do not pass `.env` to build. Alternatively `npm ci && npm run build`; standalone requires `.next/standalone`, `.next/static`, and `public/` copied to deployment directory; run `node server.js` with `HOSTNAME=127.0.0.1 PORT=3000` under an unprivileged service user. `npm run build` runs the postbuild asset preparation script, so `npm start` serves the standalone server with CSS, JavaScript and public assets in a source checkout. For a separate deployment directory, still copy all three artifact directories.
   After build, run `npm run ops:preflight` in the reviewed operator checkout with runtime `DATABASE_URL` and separately injected operator `DIRECT_URL`, both targeting the same intended project/database. Require exit0 for the full gate before release. Alternatively inspect each mode separately, then run the default full gate; runtime-only success leaves migration history unverified. Keep `DIRECT_URL` out of the app container/environment; the stripped standalone app is not the operator CLI checkout. See [operations checks](OPERATIONS_CHECKS.md).

4. On VPS, run one container: `docker run -d --name monechai --restart unless-stopped --env-file /etc/monechai/runtime.env -p 127.0.0.1:3000:3000 monechai:REVISION`. Set runtime public vars to the same values used at build. Keep Docker port loopback-only and restrict firewall; allow at least 30 seconds graceful stop time for in-flight requests when replacing container. Replace only after new instance and health checks pass; a canary should point to the same migrated schema.
5. Install TLS reverse proxy using [`ops/nginx-monechai.conf`](../ops/nginx-monechai.conf) as a template. Replace example hostname; test `nginx -t` and reload. The origin must be TLS-protected even when using Cloudflare. Cloudflare **Full (strict)** validates origin certificates ([official guide](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/)); don't use Flexible. Forward the real visitor IP only from trusted Cloudflare ranges/proxy and block direct Node access before enabling `CHECKOUT_TRUST_PROXY_IP_HEADER=true`. Leave it unset otherwise. Do not cache `/admin`, `/api/*`, `/checkout`, `/order/*`, `/en/checkout`, `/bn/checkout`, `/en/order/*`, `/bn/order/*` or session-dependent HTML at Cloudflare or the proxy. Respect `Cache-Control` and avoid 'cache everything' rules.
6. `curl -i https://shop.example.com/api/health` must return HTTP 200 and `{"status":"ok","database":"ok"}`; 503 means DB unavailable (never count as healthy). Verify public shop, nonmember/admin redirects, authenticated catalog/order journeys, valid COD order with owner-approved fees, and checkout idempotency using test fixtures, then clean fixtures. Configure an external uptime check for `/api/health` and an error tracker with PII redaction. Do not log customer names, phone, address, order tokens, cookies, request bodies or database URLs.

Rollback: keep previous immutable image; roll back app **only if schema remains compatible**. Do not run an unreviewed down migration on live orders. For destructive data changes, take traffic offline and follow [recovery procedure](backup-recovery.md). Monitor HTTP 5xx, 503 health, checkout failure rates and disk space; rotate secrets after exposure. No VPS, DNS or Cloudflare deployment has been accepted. Supabase provisioning is recorded in [the handoff](SUPABASE_SETUP_HANDOFF.md); actual owner/provider acceptance remains pending.

## Quick troubleshooting

- `/api/health` 503: verify runtime DB URL, network/TLS and migration status privately (avoid logging credentials); DB health requires a live connection.
- Admin login fails: check build-time and runtime Supabase public settings, Auth redirect allowlist, confirmed user and `admin_members` ([bootstrap](admin-bootstrap.md)).
- Missing CSS/images: ensure `.next/static` and `public` accompany standalone; verify public `products` Storage bucket and image-host build config.
- No checkout shipping quote: configure **owner-approved** rates; do not silently substitute sample prices.
